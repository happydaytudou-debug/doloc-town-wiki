# Doloc Town Wiki Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build a locally runnable, statically generated English Doloc Town guide aligned to the Level 2 submitted matrix, with one homepage, four category pages, sixteen sourced guide pages, a 404 page, responsive layouts, SEO, and documented verification.

**Architecture:** Astro generates directory-style static routes from typed site data and an MDX guide collection. Shared layouts and small Astro components render a content-first light Wiki interface; build-time validators enforce page, relationship, citation, and metadata integrity before the site is accepted.

**Tech Stack:** Astro, TypeScript, Astro Content Collections, MDX, native CSS, npm, Node's built-in test runner, Astro check, and a production static build.

## Global Constraints

- Import and audit the project owner's existing Level 1–3 materials before writing factual game content.
- Do not research game facts on the internet unless the owner later approves a named evidence gap.
- Do not invent statistics, mechanics, recipes, locations, conclusions, redemption codes, sources, or links.
- Use the site name `Doloc Town Wiki`; never imply that the site is official, endorsed, or community-maintained.
- Site copy is English; project discussion and approval are Chinese.
- Use Astro + TypeScript, Markdown/MDX Content Collections, native CSS, and npm.
- Generate one homepage; the four categories `Guides`, `Farming`, `Characters & Items`, and `Map & Quests`; the final sixteen Level 2 guide pages; and one 404 page.
- Preserve the exact submitted page name `Recipes` and slug `recipes`.
- Start every guide at page-level `Needs Verification`; broad source index pages cannot establish Verified claims.
- Use directory-style URLs with trailing slashes and base-path-safe internal links and assets.
- Default to a light, practical Wiki design with restrained post-apocalyptic mechanical details.
- Use only owner-approved official game imagery; the image-free layout must remain complete.
- First release excludes search, backend, CMS, accounts, comments, dark mode, and deployment.
- Do not initialize Git, commit, connect GitHub, push, or deploy until separately authorized.
- Commands below become executable only after the owner authorizes scaffolding and dependency installation and the required Node/npm environment exists.
- At every factual-content step, stop rather than substitute guessed copy when the imported source package is insufficient.

## Review and Change Discipline

- Each task receives an independent requirements review and a code/content quality review before the next task begins.
- If implementation uses subagents, use `superpowers:subagent-driven-development`; otherwise use `superpowers:executing-plans` with checkpoints.
- Fixes remain inside the currently rejected task until its completion standard passes.
- Do not broaden scope to search, dark mode, CMS, accounts, comments, deployment, or unrelated visual polish.
- The usual Superpowers commit step is intentionally gated: because Git operations are not authorized, do not initialize or commit during execution. If the owner later authorizes Git, create a separate reviewed version-control plan rather than retroactively changing these task boundaries.
